# Known-good open-flow build of vc707_ethmin_vm on current upstream (2026-10-14)

A bitstream built through the open flow from **plain git checkouts of upstream nextpnr and prjxray-db** (nothing hand-made, no private
branches) booted a VC707 and passed both board tests below.  This supersedes the "known good" combination in `KNOWN_GOOD.md` (2026-10-11),
which needed a private nextpnr branch (`e558304b`) and a private database branch (`bdab7fe`).

## Board results (VC707, loaded over JTAG into SRAM, UART captured by script)

* **Pi check**, 2 loads: DHCP bound, 327988-byte image fetched over NFS, REPL evaluated `355. /. 113.` to `3.141593`.  2 of 2 pass.
* **Self-compile**, 1 load: the compiler compiled `io/comp.ml` over NFS in 162 s to 729 phrases, 327988 bytes.  The image is byte-identical
  (sha256 `2fb84d96...`) to the one the host builds from the same source with `tools/selfhost_nodisk.sh`.

An earlier build on the same nextpnr with the same database content but the Artix-7 `timings` link (database `5b9a00f`, bitstream
`a6afeb26...`, same FASM) passed the pi check 3 of 3 and the self-compile once.

## What changed from `KNOWN_GOOD.md`, and why it matters

* The TX clock legs of the PHY MMCM and clkgen MMCM now ride the dedicated `CK_BUFG_CASCO` <- `CK_BUFG_CASCIN` pips of the top `CLK_HROW`
  tiles (10 such pips in this FASM; the earlier `main-s1` FASM, which I checked, has none).  Before nextpnr #104 the chipdb dropped those pips and
  router2 sent the legs through BUFH, a LUT and long lines.  The maintainer's single-change bitstreams showed that is what kills Ethernet
  TX: `fix-s1` and `fix-s4` (legs on the cascade) pass 3 of 3 each, `reroute-s1` (legs re-routed through other fabric pips) fails 3 of 3.
* The database's `virtex7/timings` is the real Virtex-7 set (51 SDF files, upstream), not a symlink into an f4pga Artix-7 install.  Earlier
  published bitstreams were built through that symlink; keep `bdab7fe` to reproduce those.
* The same FASM assembles to a different bitstream against this database than against my earlier one: `xc7vx485t/tilegrid.json` differs in
  the `bits` field of 29 tiles (for example the `LIOB18_SING` alias `start_offset`, and `CFG_CENTER_MID`).  Both bitstreams work.

## Rebuild

    git clone https://github.com/openXC7/nextpnr && git -C nextpnr checkout c4dc8713 && git -C nextpnr submodule update --init himbaechel/uarch/xilinx/meta
    git clone https://github.com/openXC7/prjxray-db && git -C prjxray-db checkout b12466df
    cmake -S nextpnr -B build -DARCH=himbaechel -DHIMBAECHEL_UARCH=xilinx -DBUILD_GUI=OFF -DBUILD_PYTHON=OFF \
          -DHIMBAECHEL_XILINX_DEVICES="xc7vx485t" -DHIMBAECHEL_PRJXRAY_DB=$PWD/prjxray-db \
          -DEigen3_DIR=/usr/share/eigen3/cmake -DCMAKE_IGNORE_PREFIX_PATH=$HOME/miniconda3
    cmake --build build --target nextpnr-himbaechel --parallel 8
    tools/progimage.sh io/netboot.ml fpga/vc707-ethmin
    SV2V=<sv2v> NEXTPNR=$PWD/build/nextpnr-himbaechel PRJXRAY_DB=$PWD/prjxray-db YOSYS_DEFS="-DSYS_DIV=20.000 -DCLK_HZ=50000000" \
        WORK=<dir> fpga/vc707-ethmin/open_build.sh

`open_build.sh` writes `provenance.txt` with the above, so compare that first.

## What this does not show

* One seed.  The earlier table (`evidence-nextpnr-seed-sweep/`) has runs on `main` with only the `.IN` fix that pass 2 of 4 seeds; a seed
  sweep on this setup has not been run, so there is no claim that the pass rate changed.
* One netlist.  The build id is a constant in the logic, so a different commit is a different netlist and placement.
* nextpnr's model does not time the cascade legs against the PHY's requirements; the board is the only measurement.
* The Virtex-7 timings have been shown to build and run here; they have not been compared against Vivado's timing for this design.

## Verification tool

The LVS equivalence (`fasm2netlist`, jrrk2/fasm2netlist `main`, merged from PR #6 (merge `f4b26a7`; this proof ran at its tip `e2fd138`, which is in `main`), CaDiCaL 3.0.1) proves the extraction of this very layout equivalent to the yosys
netlist: **63309 comparisons proved, 0 differ, 0 unknown** (973 s), with 5934 registers matched, 670 memories and 21 DSPs paired.  The extraction
traces the clock tree (the default; `--simple-clock` turns it off): for every register it holds the clock edge against the slice's `CLKINV` bit and **which BUFG
clocks it** against the traced pips to a BUFGCTRL output (5934 compared, 0 differ in each), and for every BUFG **what feeds it**: each of the 9 BUFGCTRL inputs is
followed back to an MMCM output (6), a transceiver's TXOUTCLK/RXOUTCLK (2) or a slice (the SD clock), and compared with the cell driving it in the synthesis, by tile
and pin: 9 compared, 0 differ.  Each used RAMB port's clock polarity is held against `ZINV_CLKARDCLK/CLKBWRCLK`.  The checks catch what they claim:
flipping a slice's `CLKINV`, deleting a register tile's clock pips, or moving one BUFG input to another MMCM output is reported.

The same check on the pre-#104 layouts (`vc707-bramtest`, `vc707-ocaml`, built before the cascade pips were in the chipdb) reports 1 and 4 differences: the MMCM
clock reaches the BUFG through a LUT and long lines (`LOGIC_OUTS` -> `LV` -> `IMUX` -> BUFG), not the dedicated cascade.  That is the routing the maintainer's `reroute` bitstream
shows kills Ethernet TX, found here from the FASM alone.  A pad-fed BUFG (the Johnson example) is traced to its pad tile and labelled `dedicated` or `fabric`; the latter
is a NOTE.  Extraction with the clock tree costs about 15% more time and memory (437 s -> 501 s, 3.9 -> 4.6 GB) on this layout.

Not covered by that statement: what feeds the MMCM (its `CLKIN`, the IBUFDS) and its configuration, registers not
clocked by a BUFG, an OBUFT's tri-state enable, the IBUFDS_GTE2, the transceiver configuration, and the initial contents of the
memories beyond what the bitstream rows show.  The same tool on the earlier `vc707-ocaml` layout (nextpnr `e558304b`) proved 19250 with 0
differences in 140 s, before the register clock-edge and clock-source rows existed.
